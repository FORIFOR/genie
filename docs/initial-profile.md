# 初回の Genie Profile

Google / Microsoft の最初の読取接続後に、Home の同じ領域で「接続 → 解析中 → 結果確認」を表示する。結果は現在の仕事、よく関わる人、直近の優先事項、仕事の傾向、未完了の項目の5つに絞る。確認後は Home に戻り、この初回プロファイルを自動で作り直さない。

## 読取範囲と表示

- 最初に接続したプロバイダーの、許可済みの読取接続だけを使う。送信用トークンは使わない。
- カレンダーは過去90日から今後45日。メールは直近90日。Google はアーカイブを含む受信400件・送信400件・重要／スター付き200件、合計最大1000件を上限にメタデータを読み、重複を除く。初回解析だけ1ページ100件で最大4ページずつ取得する。Microsoft は受信トレイ100件・送信済み100件までで、アーカイブは今回の対象外。全メールを網羅したという表示はしない。
- 配信解除・自動送信・一括配信のヘッダー、通知用アドレス、Googleの広告・SNS・フォーラム・更新通知ラベルを選別に使い、広告・自動通知を初回解析データから外す。Googleの4カテゴリは検索条件でも除外し、広告が候補取得枠を占めるのを防ぐ。取得後の同じ除外チェックも維持する。送信履歴から確認できる自分自身も相手の一覧に含めない。
- 双方向のやり取り、本人の送信・返信、重要指定を優先する。各スレッドの最新受信・送信を対にし、1スレッド最大2通、全体最大100通の本文を読む。対象が不足しても広告で件数を水増ししない。HTML・引用履歴・署名を減らした各2000文字までを、端末内モデルの分析にだけ使う。添付の中身は取得しない。ローカル分析が設定されていない場合は本文を取得しない。設定済みモデルの失敗は未分析として表示する。
- メール本文と抜粋はサーバへ送らず、保存・ログ出力もしない。保存するのはメタデータと、根拠のメールIDを持つ短い分析結果だけ。本文を読めなかったメールや、モデルから有効な結果を得られなかったメールを分析済みとして数えない。
- モデルが明示的に対象外と判定したメールも、本文を確認した件数に含める。モデル境界で現在の群に実在する `excluded_ids` だけを `analyzed_ids` に合わせ、既存の厳格な検証を通す。どちらにも挙がっていないメールは補わない。未知のID・重複・対象外メールを根拠とする主張は拒否し、外部APIの契約は変更しない。
- 人物情報は自己を除外して形式を検証し、差出人を優先して最大50人までに整理する。不正なメールアドレスを切り詰めて別のアドレスとして保存しない。残る契約違反のメタデータはそのメールだけ対象外にし、正常なメールの保存を巻き添えにしない。
- ローカル分析は同じスレッドの受信・返信を組に保ち、最大6件・本文合計8000文字ずつ順に行う。有効な分析結果だけを最後に案件単位へ統合し、失敗した組があれば部分分析として件数を表示する。診断ログには固定のエラー種別だけを残し、メール内容やモデルの生の応答は出力しない。
- 形式・根拠IDの検証に失敗した群は、スレッドを分断せず二つに分けて各1回再解析する。単一スレッドなら同じ群を1回だけ再解析する。初回結果が有効でも分析済み件数が群の件数に届かない場合は、0件の結果も含め、元を保ちながら同じ群を1回だけ再確認する。新しい結果が元の分析済みIDをすべて含み、件数も増えた場合だけ結果全体を置換する。失敗・同数・一部欠落なら元を保持し、二つの結果の合算はしない。再試行時は固定の形式・参照整合ルールを付け、前回の生のモデル応答は再入力しない。追加の上限は両方式で共有し、入力24件ごとに最大4回・累積120秒ずつとする（端数は切り上げ、100件では最大20回・累積600秒）。完全に分析できた群や再試行後の結果は再実行しない。回復処理の診断は件数・所要時間・予算使用状況だけを記録し、メールIDや内容を含めない。通信失敗や時間切れを無制限に繰り返さず、実際に検証を通った分だけを表示する。
- モデルには実行中だけ有効な短いメール・スレッドの参照を渡し、根拠を検証してから元IDへ戻して再検証する。統合資料は成功した群を巡回して選び、最大8000文字に収める。仕事・優先事項・未解決項目のうち候補がある分類に容量を等分予約し、余りを再配分することで、先の分類だけで枠が埋まるのを防ぐ。分析済み件数は本文分析の成功数であり、現在の仕事5件・優先事項5件・未解決項目30件の要約が、全メールの全案件を列挙するという意味ではない。
- サーバへのメタデータ送信は1回500件以下かつ本文JSON部分900KiB以下に分割し、APIの1MiB上限内に収める。進捗は送信が成功した件数とIDだけを積み上げる。
- Gmail の3種類の一覧は順に取得し、各一覧のメタデータ取得は同時4件までに制限する。初回の一覧・メタデータ・本文・再試行は同一接続の待機列を共用し、実際の通信開始を250ミリ秒以上空ける。403の `rateLimitExceeded` / `userRateLimitExceeded` と429応答を利用制限として判別し、1秒・2秒待って最大2回だけ再試行する。通常の権限拒否は再試行しない。取得・待機・分析の間も30秒ごとにリースを更新し、制限が続けば失敗として表示する。通常読取りの待ち時間を変えず、送信操作も再試行しない。失敗の診断は固定の処理段階と分類だけを記録し、提供元の生のエラー文・本文・認証情報を残さない。
- 件数は読取が完了した実件数。途中の発見数も保存済みデータから算出し、例示の数字や進捗率で補わない。
- 件名をそのまま仕事内容・優先事項へ昇格させない。分析結果には対象メールIDの照合を行い、一部だけ成功した場合や分析できなかった場合はその状態と実件数を示す。対象メールが0件なら、対象なしとして扱い、モデルの失敗とは表示しない。
- 待ち時間は本文の取得件数と端末内モデルに依存する。本文を使わなかった旧方式での約2.3秒という実測は、新しい本文分析の性能を示すものではない。

未接続・未許可のソースはその旨を表示する。一部を読めた場合は不足を示して結果確認へ進む。全ソース失敗時は再試行できる。確認前は回答向けのプロファイルとして採用せず、「この内容を使う」または編集後の保存で5項目を確定する。

分析モデルは `ASTRA_INITIAL_PROFILE_MODEL` を優先し、未指定なら Computer Use のローカル画像モデル、ローカル会話モデルの順で選ぶ。接続先は `ASTRA_INITIAL_PROFILE_URL` で指定でき、専用モデル指定時の既定は `http://127.0.0.1:11434/v1`。端末内の Ollama だけを使用し、リモートモデルへの別名も拒否する。

## 保存・再開

`initial_profiles` に tenant / user ごとに1件を保存する。開始は冪等で、再接続・アプリ再起動でも同じ状態を読む。AgentHost はジョブの有無を確認し、5分の排他的なリースで初回読取を実行する。停止した worker のリースは失効後に引き継げる。確認済みジョブは再実行しない。既存の通常データ同期とは別で、継続的なプロファイル再解析や新しい Memory 画面は追加しない。

初回解析のメタデータは専用の `artifact_snapshot` に一時保存し、通常同期の本文・推定情報・同期カーソルを上書きしない。本文取得中と分析中は件数・IDだけの進捗通知でリースを維持する。リース引継ぎ時は古い進捗とスナップショットを消し、ユーザー確認後はスナップショットを破棄して確定した5項目を残す。

実行には、新しい DB マイグレーションを適用した gateway と、同じユーザーに認証された AgentHost が必要。macOS の既存開発用サインインは再起動時のユーザーIDを維持するよう修正した。今回、新しい本番ユーザー登録・認証基盤は追加していない。

## 検証

100件対応の実機取得では、Gmail が HTTP 403 の `rateLimitExceeded` を返すことを確認した。これは接続の再承認が必要なエラーではない。Gmail の[公式利用上限](https://developers.google.com/workspace/gmail/api/reference/quota)と[エラー対応](https://developers.google.com/workspace/gmail/api/guides/handle-errors)に基づき、初回取得へ速度制御と403の正しい分類を追加した。個別プロジェクトの適用枠は未測定であり、速度制御は他のクライアントによる利用まで保証するものではない。

DB / API テストで一度だけの開始、排他実行、tenant 分離、途中の実データ集計、失敗と再試行、ユーザー編集、確認後の固定を検証する。AgentHost テストでは期間・件数上限、広告除外、返信の対の維持、Google のアーカイブ取得と Microsoft の受信トレイ・送信済みへの限定、本文の削減、モデル未提供時の本文取得なし、本文非送信、失敗件数と根拠IDの照合を確認する。通常の定期同期は従来の抜粋だけの取得から変更しない。

`GenieMac --selftest initialprofile <output-directory>` は、解析中・結果確認・編集を明暗両テーマで描画し、実際の編集ボタンを操作する。`docs/golden-screenshots/initial-profile/` の画像・geometry はこのテストの架空データであり、ユーザーの実アカウントの分析結果ではない。

旧方式のGoogle読取専用検証では、メール51件・予定7件のメタデータ取得、結果確定、同じプロファイルの再取得、再読取なし、Home API取得まで確認した。これは新しい本文分析の品質検証ではない。`scripts/reality/run-initial-profile-live.sh` は引き続き本文を取得しない読取専用ハーネスで、分析状態が unavailable・分析済み0件であることも検証する（事前の読取認証設定が必要）。Microsoft の実サービス検証と、新方式での接続開始から結果確定までの通し操作は未確認。

2026-10-10 の macOS 実機確認では、Home の再分析ボタンから Google の実アカウントを読み、広告等の除外後のメール33件・予定7件を取得した。選択24件中13件の本文分析が検証を通り、`partial` の件数と案件単位の結果を Home に表示した。本文は端末内の `qwen3.5:9b` だけへ渡し、結果の確定操作は行っていない。実アカウントの内容・画面はリポジトリに保存していない。

同日の限定再試行追加後の実機確認では、同じ Home 操作で24件中17件の本文分析が検証を通り、うち2件を分析内で対象外とした。最終結果は引き続き `partial` で、画面の17/24件表示・未確定状態を確認した。取得したメール33件・予定7件は前回と同数。根拠IDの整合性に失敗した結果は採用していない。

100件対応後の最終実機確認は2026-10-10 11:23:54〜11:31:20 JSTに行った。Homeの再分析から広告等の除外後のメール197件・予定7件を取得し、主要メール100件を選択した。うち99件の本文分析が検証を通り、17件は分析内で対象外とした。APIと実画面の両方で99/100件・`partial`・未確定状態を確認しており、100件完了とは扱わない。1件は有効な分析結果が得られていない。本文は引き続き端末内の `qwen3.5:9b` だけで処理した。長文は各2000文字まで、添付は対象外。途中の実行では77/100、98/100、97/100の結果もあり、再実行が必ず件数を増やすとは保証しない。追加の回復集計は `info` レベルのため、当該プレビューの `warn` 設定では残らず、最終1件の不足理由をその集計から特定できていない。

100件の契約境界、既存24件との互換、メタデータ送信の分割、Gmailの取得制限とページング、広告除外、スレッドの維持、短い根拠参照からの復元を対象テストで確認した。最終の分析・HTTPテスト120件、ビルド、型検査が成功し、別担当の同120件と追加13ケースの検証でも件数の水増し・根拠検証の省略は見つからなかった。macOSの実機セルフテストで100件の合成表示を確認し、明暗8画面のgoldenを更新した。実アカウントの結果画面はリポジトリに保存していない。

これは分析品質全体の合格ではない。合成メールでは、相手が引き受けた作業を本人の担当にする誤りが同モデルで残った。話者の明示と構造化出力だけでは解消せず、推論設定 `low` の比較も出力上限で未完了だった。端末内の `qwen2.5:7b` でも同じ6件の主体誤認を再現し、2件の単独スレッドでも発生したため、最後の統合処理だけの問題ではない。形式・根拠IDの検証は意味内容の正しさを保証しない。最終実メールの未分析1件と、担当者・未着手／進行中の判定品質は未解決として扱う。別の外部モデルへ本文を送る場合は、送信対象と送信先について利用者の承認を得るまで実行しない。
