# Orca integration (PR 1–3)

`@genie/worker-agent-host` exports `OrcaAdapter` for a local Orca runtime. It wraps the documented `orca status`, `repo add`, `terminal create`, `terminal send`, and `search` commands. The adapter requires an absolute Orca executable path and explicitly configured workspace roots. It resolves symlinks before accepting a project path. CLI output and errors are not logged; errors returned to callers contain only a generic reason.

The local API supports readiness, new project creation with Git initialization, existing repository registration, starting Claude or Codex in an existing workspace, searching indexed sessions, and opening a terminal with the provider's session resume command. `create` only accepts a single new directory name under an explicitly configured root; it never overwrites an existing directory. `launch` and `resume` return a terminal handle, which is an acknowledgement that a terminal opened, not proof that coding completed. Orca must be installed and running on the same host. The public Orca CLI does not document a direct session resume command, so this adapter uses `terminal create` with `claude --resume <id>` or `codex resume <id>`.

Genie does not call `orca agent launch`: Orca documents that normal agent launches may apply full-autonomy flags. The adapter explicitly starts Claude with `--permission-mode manual` and Codex with `--sandbox workspace-write --ask-for-approval on-request`. A worktree is not a security sandbox. Operators must still use OS sandboxing or a dedicated account to restrict writes outside the project.

The `coding.orca.status`, `search`, `create`, `register`, `launch`, and `resume` task kinds run through Genie's existing Temporal task workflow and the local Agent Host. Every request includes `host_id` and is routed only to that user's host. Create, register, launch, and resume require an approval bound to the operation and its exact input, with one execution attempt. Approval revocation is checked again before the host runs it. Search returns only the agent, exact project path, session ID, update time, and message count; transcript evidence and resume commands are discarded.

These tasks record a project registration or terminal receipt as their result. A successful `launch` or `resume` means Orca opened a terminal; it does **not** mark the coding work complete. The existing `AgentJobs` coding jobs and their Claude/Codex adapters remain separate. The Orca fallback monitor observes the first launched turn; project/session registry and native Orca UI controls remain later stages.

An authenticated Genie client can create a status task with `POST /v1/tasks`, an `Idempotency-Key` header, and `{ "kind": "coding.orca.status", "input": { "host_id": "<Genie Agent Host UUID>" } }`. As with any task, HTTP 202 means accepted; the client must query `GET /v1/tasks/:taskId` for the final state. The local Agent Host must be running. Its result distinguishes `reachable: false` from a reachable Orca runtime.

For a launch that may switch on quota, include `"fallback_agent": "codex"` with `"agent": "claude"` (or the reverse). The chosen fallback is shown in the exact-argument approval. Genie first asks the selected agent's own signed-in CLI for a small, read-only JSON response. A definite `rate_limited` response selects the fallback before launch. If the primary starts, the Agent Host continues to observe that first turn through Orca. On a rendered usage-limit signal, it checks the fallback's availability, atomically claims the one replacement, stops and confirms the original terminal is gone, then launches the approved fallback with instructions to inspect existing work and continue only unfinished parts. An ambiguous result or interrupted switch is recorded as uncertain and is never auto-retried. Monitoring resumes after an Agent Host restart; the original approval must still be valid. The launch result artifact records the initial agent; `GET /v1/tasks/:taskId/orca-supervision` reports later monitoring and handoff state. A fallback is never added silently, because it can use a different paid account.

When the task owner has a linked LINE DM, API-created Orca mutation tasks join the existing durable task notification outbox. Completion, failure, and approval notices use the same channel machinery as other tasks. A later handoff, blocked alternative, or uncertain switch creates one additional deduplicated LINE notice. Neither the launch receipt nor the switch notice claims that coding work finished. The LINE route is not available if the owner has not linked LINE or the channel is not configured.

A linked owner's LINE DM can also create a `coding.orca.launch` task directly from a deliberate coding request that names Claude or Codex. The configured `GENIE_LINE_ORCA_PROJECT` is the only target path; the gateway chooses exactly one online host belonging to that owner, and a missing or ambiguous host produces an explanatory reply without creating a task. If several hosts are online, `GENIE_LINE_ORCA_HOST_ID` selects one. The first named agent is primary. A second named agent is approved as fallback only when the message explicitly requests a switch on a limit. The original LINE event ID supplies task idempotency. Execution still waits for the existing Genie approval card (`REVERSIBLE_WRITE`); LINE approval buttons are not used for local code changes. In managed preview, the checked-out Genie repo is the default LINE target only when it lies inside the explicit `--orca-root`. Another target can be supplied through `GENIE_LINE_ORCA_PROJECT` in `--channels-env`, and startup validates it stays inside that root.

For the managed preview, use `--orca-root /absolute/project/parent` to pass one allowed parent folder to its Agent Host. For a manually started Host, set `ASTRA_ORCA_WORKSPACE_ROOTS` to a JSON array of absolute allowed roots, for example `["/Users/me/Projects"]`. `ASTRA_ORCA_PATH` can specify an absolute CLI path; otherwise the host checks absolute directories on `PATH`. Orca's Session History indexing must be enabled on that host for search and resume. Examples of task input (each wrapped in `{ "kind": "coding.orca.…", "input": … }`):

| Kind       | Input                                                                                                                                               |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`   | `{ "host_id": "<host UUID>" }`                                                                                                                      |
| `create`   | `{ "host_id": "<host UUID>", "root": "/Users/me/Projects", "name": "new-app" }`                                                                     |
| `register` | `{ "host_id": "<host UUID>", "path": "/Users/me/Projects/app" }`                                                                                    |
| `launch`   | `{ "host_id": "<host UUID>", "path": "/Users/me/Projects/app", "agent": "codex", "prompt": "Implement authentication" }`                            |
| `search`   | `{ "host_id": "<host UUID>", "path": "/Users/me/Projects/app", "agent": "codex", "query": "authentication" }`                                       |
| `resume`   | `{ "host_id": "<host UUID>", "path": "/Users/me/Projects/app", "agent": "codex", "query": "authentication", "session_id": "<search result UUID>" }` |

Resume confirms that the session ID appears in Orca's search results for the same project and agent before opening it. Launch and resume refuse to open another writable agent terminal in that project. An operator can stop a running terminal in Orca; cancelling a task after a terminal opens does not stop the coding agent.
If Codex asks to trust a newly created folder, the task fails with `orca.workspace_trust_required` and retains the open terminal handle. The prompt has not been sent. Review the folder and decide in Orca; then continue in that terminal. If prompt delivery cannot be confirmed after a terminal opens, the task fails and retains the terminal handle for inspection. Neither state is retried automatically.

## Local validation (2026-11-17, macOS arm64, Orca 1.4.261)

Orca was installed from the official Homebrew cask and the runtime reached `ready`. `repo add` registered the Genie Git repository. The terminal CLI returned `result.terminal.handle`; a Claude terminal reached `tui-idle`. Claude then reported a weekly usage limit, so Claude's prompt completion remains unverified. A Codex terminal accepted a short read-only prompt and replied `READY`. A search for that prompt found the Codex session, and `resume` reopened the same session in the same project. Orca's session index was enabled locally for this check. The initial plain `codex` launch showed YOLO mode; after adding explicit sandbox and approval flags, Codex `/status` showed `Workspace (Ask for approval)`.

CLI command reference: [Orca CLI](https://orca.dev/docs/cli/reference), [session history](https://orca.dev/docs/agents/session-history).
