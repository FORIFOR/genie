**これは目標と受け入れ条件であり、実サービス合格の宣言ではない。** 背景入力の根拠は [10月1日の検証](VISIBLE_COMPUTER_POINTER.md)、取引経路の現在の証拠は [10月2日の検証計画と記録](evidence/2026-10-02-transactions/VERIFICATION_PLAN.md)。この目標の提示は、個別の実注文・支払い・証券売買を行う指示ではない。

## 公式注文サイトへの限定的な入口

接続済みのmacOS Homeでは「マクドナルドの注文画面を開いて」「マクドナルドの注文サイトを開いて」「ドミノの注文画面を開いて」のように明示する。既存のHome実装は注文画面・注文サイトという語をローカル準備フローから除外するため、通常の会話APIへ渡す構造になっている。**この到達性はソースで確認したもので、今回の新経路の実Home操作・ブラウザ表示の合格ではない。** 通常の「マクドナルドを注文して」は既存のローカル準備画面を維持する。ドミノにはそのローカル捕捉がなく、厳密に対応する直接依頼は新しい引き継ぎへ進む。ローカル準備画面から送る `consumerPlanning` 付き提案経路とは別である。

公開契約は `service` の列挙値だけを受け取り、入力URL・ログイン情報・注文内容・支払情報は受け付けない。ローカルホストは固定の[マックデリバリー入口](https://www.mcdonalds.co.jp/mcdelivery/)または[ドミノの配達注文入口](https://internetorder.dominos.jp/delivery)を `open -g -u` に渡す。ブラウザの強制前面化は要求しない。OSコマンドの成功はページ表示を証明しないため、結果は `navigation=requested`、`prepared=false`、`orderStatus=not_submitted`、認証・カート・履歴は `not_checked` のままとする。

成果物とタスク名は「注文画面への引き継ぎ（未注文）」。サイト上で確認すべきログイン／顧客情報、配送先、日時、商品、総額、支払方法を案内し、最終操作を利用者へ渡す。自動カート準備ドライバー・本番注文アダプターの不足は解消していない。失敗時も注文は送っておらず、自動再試行や汎用Computer Useへの切り替えは行わない。株の実注文経路は追加していない。検証の範囲は[限定入口の記録](evidence/2026-10-02-completion/CHECKOUT_HANDOFF.md)を参照。

## 毎回の確認を減らす

「今回だけ」と「同じ条件で任せる」を分ける。後者は最初に利用者が明示的に選び、注文先・口座・商品と数量・選択肢・配送先・支払方法・受取条件を固定する。1回の上限、累計の上限、回数、期限のすべてを満たす注文には、その設定から正確な見積もりに結び付く承認を作る。設定を作った今回の注文も回数と金額に含む。範囲外では通常の確認に戻る。

現在の限定委任は **課金のないシミュレーション専用**。期限は最大30日。設定画面から取り消せる。設定の作成・取消は人が操作するAPIで、モデルのツールには公開しない。許可を記したWebページやモデルの出力で範囲を広げない。

同時実行でも上限を超えないよう、予約台帳と個別承認を同じDBトランザクションで保存する。通信の再試行には同じ作成IDを使い、設定や予算枠を増やさない。結果未確認・失敗・停止した注文も、予約した回数と金額は戻さない。取消後は実行層の継続確認で以後の入力を止める。既に送信・受理された注文の取消を意味しない。

OSの初回権限、操作対象の選択、追加ログイン認証は別の境界である。現行の模擬注文画面は同じホスト内で一つの所有プロセスとウィンドウを再利用し、注文を直列に処理する。[本番ヘルパーによる直接試験](evidence/2026-10-02-transactions/NATIVE_SESSION_REUSE.md)では、初回の通常同意後、異なる模擬注文2件を同じPID・ウィンドウで受け付け、2件目に対象選択を出さなかった。注文ごとに操作表示を終了し、古い注文のボタンは無効にする。

この再利用は現在の所有セッションに限る。5分間の待機、利用者による画面の終了、実行中の停止、ホストの終了ではそのプロセスを閉じ、新しい対象には再び選択が必要になる。[主アプリの後続試験](evidence/2026-10-02-transactions/MAIN_APP_BOUNDED_REUSE.md)では、初回に1件1500円・累計3000円・2回・24時間の設定と対象選択を行い、同じPID・ウィンドウで模擬ピザ2件を受付・結果表示まで確認した。2件目に承認カードや対象選択は出ず、上限後の3件目は通常確認へ戻り、断った後はCANCELLED・受付記録なしだった。

それ以前に1件目の後で模擬画面が終了し、2件目が新しい対象の同意を求めた[観測](evidence/2026-10-02-transactions/FIXTURE_SESSION_EXIT.md)も保持する。後続試験は対象が生存中の再利用の根拠であり、終了後の同意まで不要にはしない。また、3件目を実行前に断った結果は、実行中の停止状態を修正する試験の代わりにはしない。「完全に確認不要」とは案内しない。

## 共通の実行契約

既存の Task / Approval / ActionReceipt を拡張して接続し、UI・CLIに業務ルールを重複実装しない。以下を実装・検証する。現在の transaction 契約は実験段階であり、安定した公開APIではない。

- 注文条件と確認時の明細を別に保持する。注文先・アカウント・通貨・商品・金額・配送先または口座・有効期限を、一つの変更検出可能な注文版に結び付ける。AI利用料の上限を注文代金の上限と混同しない。
- 飲食注文は、利用者が注文先・内容・配送先・予算を具体的に許可した範囲で確定まで進める。この許可を注文版に結び付く承認記録として検証し、既存の高リスク操作の承認を省略しない。範囲不足、値上がり、商品・配送先変更、追加契約などは、その変更内容を示して必要な確認を取る。ボタンごとの確認は完成条件にしない。
- 確定の直前に、信頼できる実行層で注文版・許可・期限・上限を再検証する。対象サービスのドメイン／アプリ・確定操作を実装側で識別する。ページ内の指示やモデルの自己申告は権限を増やさない。
- 確定の試行前に永続的な記録を置く。試行中の切断・再起動・応答喪失は「結果未確認」として注文先の履歴を照会する。新しいタスクIDや別ウィンドウでも同じ注文を自動で再発注しない。UI操作だけで外部サービスの exactly-once を保証したとは言わない。
- 注文先の受付・注文履歴に根拠が得られるまで完了にしない。照会不能なら未確認を保持する。株は注文受付を約定と表示しない。
- 停止は将来の入力を止める。受付済み注文を取り消したことにはしない。注文取消は提供元の可否と結果を別に確認する。
- ログインや追加認証が必要なら利用者に引き継ぎ、復帰時に注文版を再検証する。認証情報・カード情報をモデル用ログや試験証拠へ保存しない。

## 合格させる縦一貫フロー

最初は外部課金のない架空の配達注文で、実アプリの依頼 → 承認 → Computer Use → 注文確定 → 注文履歴照合 → 利用者への結果表示を接続する。検証用の画面だけを特別扱いして承認を省略しない。次に選定した実サービスの同じフローを検証し、株は模擬取引を別ゲートにする。

| ID | 受け入れ条件 | 必要な証拠 |
| --- | --- | --- |
| T1 | 指定商品・選択肢・配送先・総額が一致し、一度だけ受け付けられる | アプリ表示、実行記録、注文先の受付・履歴の一致 |
| T2 | 欠品・価格変更・配送不可・予算超過を黙って置き換えない | 変更を注入した試験と、確定入力が出ていない記録 |
| T3 | 二重クリック、同時実行、確定直後の切断・プロセス終了でも再注文しない | 障害注入、再起動後の照会、注文先の件数確認 |
| T4 | 追加認証、人の介入、停止、再開後も古い画面・許可で確定しない | 実画面試験と入力・注文記録の照合 |
| T5 | 受付済み／未確認／取消／配送完了を正しく表示する | 提供元の状態別の実記録。受付を配送完了にしない |
| T6 | 株の模擬注文で受付・一部約定・約定・取消競合を区別する | 模擬証券側の注文・約定台帳との照合。本番成功の証拠に流用しない |
| T7 | 背景実行中の可視性と人の並行作業を維持する | 人による並行入力・IME・停止の実機試験 |
| T8 | 現revisionの製品全体の検証が通り、同じ候補を配布できる | 全体ゲート、配布物、revision、GitHubの対応確認 |

T1〜T8 の実行結果は [今回の証拠](evidence/2026-10-02-transactions/VERIFICATION_PLAN.md)から参照する。対応サイト・対象OS・自動化できる範囲を明示して判定し、模擬環境の合格から任意サービスの完遂を推定しない。

## ローカルで試す

`node scripts/start-local-preview.mjs --computer-use --transaction-simulation` で、架空の注文先を明示的に有効にする。ローカルDockerの別contextを使う場合は `--docker-context NAME`、専用データは `--state-dir PATH` で指定する。contextは切り替えず子プロセスだけに適用する。

起動したGenieへ「模擬ピザを注文して」「模擬バーガーを注文して」「模擬株を注文して」のいずれかを依頼する。これは固定の検証用商品であり、実店舗・配送・課金・証券売買は発生しない。明細を確認して模擬注文を承認した後、対象選択では **Genie 模擬注文 — 課金なし** だけを選ぶ。登録された模擬アダプターが、そのプロセスと注文版に結び付くボタンを背景操作する。モデルが任意サイトの購入ボタンを選ぶ試験ではない。

CLI経路は `node scripts/transaction-use.mjs --help` を参照する。受付応答を失った場合は同じrun-fileの `recover`、注文結果を確認できない場合は同じorderKeyの `reconcile` を使用する。再度demoを作成すると別の注文になるため、再試行の代わりには使わない。

コードの回帰検証は `bash scripts/verify-transactions.sh`。使い捨てDBの `TEST_DATABASE_URL` と `TEST_IDENTITY_DATABASE_URL` がある場合は実DB・HTTP検証も実行する。指定がない場合、DB試験を実行しなかったことを明示する。このコマンドは実画面・実ユーザー・実注文の合格を宣言しない。

重複防止の範囲は同じ永続journalを共有するホストと、provider/mode/account/orderKeyの一致内に限定する。異なる端末の独立journalや新しいorderKeyの意味的な重複は保証しない。将来の本番接続には提供元の冪等キー・確実な注文照会、または共有の業務ID排他が必要。journalの削除は発注試行の記憶を失わせるため、結果未確認の注文が残る保存先を削除しない。
